# 3. Аудит по этапам

## Этап 0 — постановка задачи и архитектура

Основной инженерный тезис остаётся правильным: нельзя оценивать только длину программы, если для её понимания требуется ещё спецификация, интерпретатор, абстрактная машина или иная заранее общая система понятий.

Размер исходного кода Go/Python по-прежнему нельзя считать нейтральной загрузочной стоимостью.

### Уточнение полной стоимости

Историческая запись

```text
C = S + B + P
```

сохраняется как схема учёта, но точное численное утверждение относится к конкретному передаваемому объекту при явно заданном профиле `A`:

```text
C | A = |M_A|
```

Если роли можно честно разделить:

```text
C | A = (S | A) + (B | A,S) + (P | A,S,B)
```

Если спецификация и исполняемая загрузочная основа неразделимы:

```text
C | A = (SB | A) + (P | A,SB)
```

### Главный урок близких проектов

Lincos показывает постепенное введение смысла через примеры. DeVito–Oehrle подчёркивает роль предварительных знаний. Lingua Cosmica показывает, что типы и логические ограничения могут уменьшать неоднозначность. CosmicOS особенно близок исходной цели NEX, потому что строит сообщение как переход от математики и логики к программам и симуляциям.

Из этого следует двухслойная архитектура:

```text
учебно-загрузочное сообщение
        -> освоенный NEX-1 Core
        -> канонические программы NEX
```

Core — точная конечная вычислительная система. Отсутствующий слой — конечная последовательность, которая учит получателя её смыслу.

### Терминология

Глобальная минимальность не доказана. В исследовательской документации используется «компактное» или «малое экспериментальное ядро».

**Итог этапа 0:** постановка сохраняется; уточнены модель стоимости и роль учебного слоя.

## Этап 1 — канонический бинарный формат

Бинарная грамматика остаётся однозначной и самоделимитируемой вместе с `U(n)`.

Длины префиксов конструкторов:

```text
2, 2, 2, 3, 4, 4
```

Сумма Крафта:

```text
3 * 2^-2 + 2^-3 + 2 * 2^-4 = 1
```

То есть пространство верхнеуровневых префиксов занято полностью.

`U(n)` корректно задаётся как гамма-код Элиаса для `n+1`.

Следствие для будущей оптимизации: сократить префикс `Prim` бесплатно нельзя. Нужно менять другие коды или структуру грамматики. Поэтому в будущем следует отдельно считать стоимость префикса `Prim` и `U(p)` идентификатора примитива.

**Итог этапа 1:** дефект бинарного формата не найден.

## Этап 2 — область действия и типизация

Для чистого Core выбор HM ранга 1, обобщения в `Let`, свежей инстанциации, унификации и occurs check остаётся обоснованным.

`fix : forall a. (a -> a) -> a` допускает расходимость, но сам по себе не разрушает типовую безопасность.

### Исправление аргумента против SK/SKI

Комбинаторная логика не является принципиально несовместимой со статической типизацией. Hindley получил наиболее общие схемы типов для объектов комбинаторной логики.

Чистый SKI можно не выбирать по другим причинам: bracket abstraction способен увеличивать термы, NEX хочет прямые `Let`, натуральные значения и типизированные операции над данными, а размер базиса сам по себе не определяет полную стоимость передачи.

### Недостающее формальное доказательство

Классические результаты HM не являются автоматическим доказательством для точных примитивов и правил вычисления NEX. Пока отсутствуют отдельные доказательства:

```text
канонических форм
сохранения типов
подходящей теоремы прогресса/безопасности для частичных вычислений
```

Если позже появятся изменяемые ссылки или состояние, текущую схему обобщения `Let` нельзя переносить без пересмотра.

**Итог этапа 2:** дефект текущего чистого Core не найден; формальная метатеория остаётся открытой задачей.

---

## Этап 3 — слабый вызов по имени

Нормативная семантика остаётся внутренне согласованной: нет вычисления под `Lam`, аргументы и `Let` задерживаются, примитивы принудительно вычисляют только нужную часть, поля пар и суммы ленивы, общая рекурсия задаётся `fix`.

Литература по call-by-need хорошо мотивирует разделение результатов как реализационную оптимизацию, но не заменяет доказательство для точного набора примитивов NEX.

Корректная текущая формулировка:

> экспериментальная реализация по необходимости сохранила все проверенные наблюдаемые результаты NEX.

**Итог этапа 3:** дефект динамической семантики не найден; формальное доказательство эквивалентности ещё требуется.

## Этап 4 — эмпирическая проверка

Точные результаты замороженного корпуса сохраняются:

```text
17 программ
345 узлов AST
1371 бит

Prim 460
Var  286
App  264
Nat  244
Lam   84
Let   33
```

Это свойства конкретного корпуса, а не частоты конструкций в программном обеспечении вообще.

`Nat(255)=21 бит` против 2300 бит у проверенной цепочки `succ` остаётся сильным аргументом за прямой `Nat` против этой конкретной альтернативы, но не доказывает глобальную оптимальность гамма-кода.

Точка безубыточности `Let` остаётся корректным локальным результатом.

На общем чистом лямбда-подмножестве:

```text
NEX 37 бит
BLC 30 бит
```

Глобального победителя это не определяет.

Результат

```text
226151 -> 2484
```

означает сокращение проектного счётчика переходов вычислителя на 98,90%, а не ускорение реального времени выполнения на 98,90%.

**Итог этапа 4:** измерения сохраняются; область применимости формулировок уточнена.

## Этап 5 — независимое восстановление и загрузочная основа

Процедура независимости остаётся сильной: пакет зафиксирован, вторая реализация была изолирована от `reference/go`, Python-артефакт заморожен до сравнения, сравнивались только переносимые наблюдения.

Результат сохраняется:

```text
942 совпадения
0 семантических расхождений
0 ресурсных асимметрий
```

Состав случаев:

```text
17   программ корпуса
325  корректных случаев = 25 наборов параметров × 13 шаблонов AST
100  статических ошибок = 25 наборов × 4 семейства ошибок
500  случайных форм термов на уровне бинарного кодека
```

Правильная формулировка:

> сильное дифференциальное свидетельство восстанавливаемости на проверенной области.

Это не доказательство полной корректности обеих реализаций и не доказательство полноты спецификации.

Наблюдение `Function` специально грубое: оно не показывает, является ли функция лямбда-замыканием или ненасыщенным примитивом. Поэтому будущая исчерпывающая проверка должна тестировать возвращаемые функции через контексты применения, а не только по метке `Function`.

### Уточнённые предпосылки

Историческая v0.1 сохраняется как артефакт этапа. Текущая модель:

```text
A0       точный бинарный кадр
A1       только базовые натуральные числа и конечные последовательности
A1(R)    A1 + точно заданное формальное исчисление R
A2(U)    A1 + точно заданная универсальная машина U и формат входа
A_host(H) земная инженерная среда
```

`A1(R)` и `A2(U)` — разные ветви. Даже математика в `A1` является объявленной исследовательской предпосылкой, а не утверждением о том, что любой разум обязан представлять её одинаково.

### Отрицательный результат по bootstrap

Ни один полный нейтральный загрузочный кандидат на этапе 5 не принят. Этот вывод после аудита становится только сильнее: прежнему варианту `A1` действительно не хватало формального языка, интерпретацию которого он скрыто предполагал.

**Итог этапа 5:** эксперимент сохраняет значение; формулировки и модель prior стали строже.

# 5. Рекомендация для следующего этапа

Повторное сравнение с Lincos, CosmicOS и другими системами меняет главный приоритет.

Точный **целевой язык** у нас уже есть. Главный недостающий компонент исходной идеи — **учебно-загрузочное сообщение**, которое переводит получателя от объявленного prior к проверяемой компетенции NEX.

Следующий этап следует формулировать как:

```text
предпосылки A
  -> конечное учебно-загрузочное сообщение T
  -> восстановленная компетенция NEX
  -> conformance / самопроверка
  -> канонические программы P
```

Основные направления:

1. определить отдельный учебный слой над стабильным NEX-1 Core;
2. построить прогрессивную последовательность уроков с учётом опыта Lincos и CosmicOS;
3. использовать типовые суждения и conformance-примеры как ограничения смысла и самопроверку;
4. определить операционный критерий «умеет программировать в NEX»;
5. построить конечный машинно-читаемый учебный артефакт и измерить его точную длину.

Параллельно должны усиливаться доказательства:

- формальная метатеория NEX;
- формальная эквивалентность допустимого call-by-need;
- ограниченно-исчерпывающая проверка малых программ и функциональных контекстов;
- внешние и контрольные наборы задач.

Несовместимый редизайн Core следует отложить, пока новые данные прямо не покажут его необходимость.

# 6. Итог аудита

Исследовательская программа этапов 0–5 выдержала полный повторный обзор литературы. Фундаментальной ошибки языка не найдено.

Сильнейшими сторонами остаются исполняемые правила wire/static/dynamic, сохранение отрицательных результатов, явный учёт предпосылок, слепая независимая реализация и отказ выдумывать размер bootstrap.

Главный пробел теперь формулируется точнее: **у NEX есть строгий вычислительный Core, но ещё нет строгого учебного курса, который способен научить этому Core неизвестного получателя**.

Именно этот пробел, а не историческая новизна, должен стать предметом следующего этапа.
