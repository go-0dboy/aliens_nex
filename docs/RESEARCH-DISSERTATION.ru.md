## Аннотация

В работе исследуется вопрос о том, может ли очень небольшое, архитектурно-независимое и статически типизированное вычислительное ядро уменьшить объём информации, необходимой для передачи исполняемого программного знания между сторонами, которые не могут предполагать наличие общего языка программирования, архитектуры процессора, ABI, операционной системы, текстовой нотации или общей среды реализации. Объектом исследования является представление и восстановление вычислений общего назначения в условиях крайне ограниченного канала передачи. Цель оптимизации определяется не только размером программ, а полной информационной стоимостью

```text
C = S + B + P
```

где `S` — информация, необходимая для задания вычислительной системы, `B` — архитектурно- и платформенно-независимая bootstrap-информация, необходимая получателю для её реализации, а `P` — объём передаваемых программ.

Разработанная экспериментальная система NEX-1 v0.1 использует шесть канонических конструкторов термов (`Var`, `Lam`, `App`, `Let`, `Nat`, `Prim`), индексы de Bruijn с нуля, rank-1 let-полиморфизм Hindley–Milner, прямые литералы натуральных чисел, произведения и суммы через фиксированные примитивы, общую рекурсию через `fix`, самоделимитирующееся префиксное бинарное представление и слабую семантику call-by-name. Теоретическая основа включает безымянную lambda-нотацию de Bruijn [1], Binary Lambda Calculus как эталон компактного бинарного lambda-представления [2], вывод типов Hindley–Milner и principal type schemes [3,4], типизированную рекурсию в духе PCF/LCF [5], универсальные коды Elias [6], а также классические различия между call-by-name и ленивыми вычислениями с sharing [9–11].

Исследование выполняется через исполняемые этапы. Stage 1 задаёт канонический wire-кодек, conformance-векторы и разделяет некорректность языка от resource-limit реализации. Stage 2 реализует проверку замкнутости, principal type inference, унификацию, occurs check и типовые схемы примитивов. Stage 3 определяет и реализует слабую call-by-name динамическую семантику с проверками ленивости и рекурсией через fixed point. Stage 4 замораживает benchmark-корпусы и правила измерения до оптимизации, после чего эмпирически оценивает текущий дизайн и контролируемые альтернативы.

На замороженном корпусе v0.3 из 17 программ канонические NEX-программы занимают 1371 бит при 345 AST-узлах. Наибольший измеренный вклад дают ссылки на примитивы — 460 бит (33,6%), далее `Var` — 286 бит (20,9%), `App` — 264 бита (19,3%), `Nat` — 244 бита (17,8%), `Lam` — 84 бита (6,1%), `Let` — 33 бита (2,4%). `Let` демонстрирует измеримую точку окупаемости и не является безусловно выгодным или безусловно лишним. Прямые `Nat(n)` значительно превосходят протестированное построение через повторный `succ`; для `n = 255` канонический literal занимает 21 бит против 2300 бит у проверенной цепочки `succ`. Экспериментальная передача только principal root type добавляет к корпусу 134 бита, то есть 9,77% program-payload overhead, однако это не доказывает, что explicit typing уменьшит bootstrap настолько, чтобы компенсировать этот рост.

На одинаковом чистом lambda-подмножестве из трёх программ Binary Lambda Calculus оказался компактнее NEX: 30 против 37 бит. Следовательно, NEX не может утверждать универсальное превосходство по размеру программ. Проектный tiny postfix stack baseline использует 1529 бит на полном корпусе против 1371 у NEX, однако эта структурная альтернатива переиспользует соглашения NEX для целых чисел и primitive IDs и поэтому не является независимым сравнением полной bootstrap-стоимости. Экспериментальный call-by-need evaluator сохраняет те же наблюдаемые weak-head результаты для всех 17 принятых программ и уменьшает число reference-evaluator transitions с 226151 до 2484 в сумме (98,90%), причём основной выигрыш сосредоточен в рекурсивных задачах и повторно форсируемых вычислениях. Это результат о реализации, а не о стоимости передачи.

Не менее важен главный отрицательный результат: полная информационная стоимость `C` пока численно неизвестна. `P` измеряется точно для выбранного корпуса, но размер Markdown-спецификации является лишь текстовым proxy для `S`, размер Go-реализации — лишь host/reference proxy `R`, а реальный receiver-neutral bootstrap `B` остаётся неизвестным. Поэтому работа не утверждает, что NEX глобально минимален, глобально компактнее Binary Lambda Calculus или оптимален по целевой функции полной стоимости. Основной научный вклад текущего этапа состоит в создании исполняемой, фальсифицируемой и воспроизводимой исследовательской системы, в которой такие сильные утверждения в будущем можно будет проверять, а не предполагать.

**Ключевые слова:** минимальный язык программирования, архитектурно-независимые вычисления, Binary Lambda Calculus, индексы de Bruijn, Hindley–Milner, кодирование программ, bootstrap, информационная стоимость, call-by-name, call-by-need, conformance, воспроизводимый benchmark.

# 1. Введение

## 1.1 Мотивация исследования

Большинство языков программирования и форматов исполняемого кода предполагают значительный общий контекст: кодировки символов, текстовый синтаксис, модель процессора, размер слова, object format, сервисы операционной системы, соглашения компилятора или спецификацию виртуальной машины. Для обычной земной разработки это естественно. Но это становится проблемой в сценарии связи, где отправитель и получатель могут разделять только упорядоченный битовый канал и базовые математические закономерности.

Поэтому мотивирующий мысленный эксперимент NEX намеренно доведён до предела: как передать не просто данные, а повторно используемое вычислительное знание, если нельзя предполагать знание земного языка, CPU, ABI, операционной системы или исходной нотации?

Наивным решением было бы минимизировать только длину программы. Этого недостаточно. Однобитная программа бесполезна, если для её понимания требуется огромная система, семантика которой получателю не сообщена. И наоборот, чрезвычайно маленький интерпретатор может сделать все последующие программы намного длиннее. Поэтому проект рассматривает задачу как совместную стоимость:

```text
C = S + B + P
```

Эта модель пока намеренно абстрактна. На текущем этапе `P` можно измерять непосредственно для канонических программ NEX, тогда как `S` и особенно `B` пока описаны лишь частично. Отсутствие корректного скалярного значения для всех трёх величин рассматривается как нерешённый научный результат, а не заполняется искусственным нулём или размером исходников host-языка.

## 1.2 Научная проблема

Научная проблема состоит в определении того, может ли компактное типизированное функциональное ядро дать выгодный баланс полной информационной стоимости для передачи вычислений общего назначения без предположения о совместной платформе реализации.

Проблема включает несколько связанных аспектов:

1. **Компактность представления.** Программы должны иметь малое, однозначное и самоделимитирующееся бинарное представление.
2. **Восстанавливаемость семантики.** Получатель должен восстанавливать scope, типы и смысл выполнения из переданных правил, а не из скрытых host-предположений.
3. **Вычислительная выразительность.** Core должен сохранять общую рекурсию и композиционное построение данных.
4. **Проверяемость.** Некорректные или плохо типизированные программы должны детерминированно отвергаться.
5. **Стоимость bootstrap.** Экономия program bits не должна оцениваться отдельно от стоимости задания и реализации языка.
6. **Эмпирическая фальсифицируемость.** Заявления о компактности должны проверяться на фиксированных workload и явных альтернативных baseline, а не выводиться из эстетики минимализма.

## 1.3 Объект и предмет исследования

**Объект исследования:** архитектурно-независимое представление и выполнение вычислений общего назначения в условиях крайне ограниченной передачи информации.

**Предмет исследования:** компромиссы между размером формальной спецификации, сложностью receiver bootstrap, размером передаваемых программ, статической проверяемостью и стратегией вычисления в минимальном типизированном lambda-core.

## 1.4 Цель исследования

Цель — построить и эмпирически оценить минимальное исполняемое ядро, чья семантика и бинарная форма достаточно явны для независимого восстановления, и одновременно создать воспроизводимый метод проверки того, способна ли его полная коммуникационная стоимость превзойти альтернативные вычислительные представления.

## 1.5 Задачи исследования

Для достижения цели поставлены следующие задачи:

1. определить минимальный архитектурно-независимый Core и его инварианты;
2. определить каноническое самоделимитирующееся wire-представление;
3. реализовать исполняемое encode/decode conformance;
4. определить и реализовать статическую проверку scope и типов;
5. определить и реализовать динамическую семантику без скрытого машинного поведения;
6. создать language-neutral conformance-артефакты;
7. замораживать benchmark-корпусы до сравнительных оптимизаций;
8. измерить стоимость отдельных конструкторов и внутренних проектных решений;
9. сравнить выбранные внешние и структурные baseline при явных предположениях;
10. отделить точный program cost от implementation/bootstrap proxy;
11. установить, какие решения подтверждаются, опровергаются или остаются нерешёнными;
12. сохранять результаты в живой исследовательской рукописи, не удаляя отрицательные результаты при развитии проекта.

## 1.6 Исследовательские вопросы

**RQ1.** Можно ли задать небольшому типизированному lambda-core детерминированное, архитектурно-независимое и самоделитирующееся бинарное представление с исполняемыми conformance-тестами?

**RQ2.** Можно ли восстанавливать статическую корректность и principal types без передачи обычных type annotations в термах?

**RQ3.** Может ли динамическая семантика оставаться простой и нестрогой, при этом допуская существенно более эффективные реализации, сохраняющие наблюдаемые результаты?

**RQ4.** Какие конструкции текущего Core дают основной вклад в transmitted-program cost и оправдывают ли себя на практике неочевидные для «минимального» языка конструкции `Let` и прямой `Nat`?

**RQ5.** Как program payload NEX соотносится с выбранными альтернативными кодировками в контролируемых и явно ограниченных сравнениях?

**RQ6.** Можно ли уже численно оценить полную функцию `C = S + B + P`, а если нет — какие доказательства ещё отсутствуют?

## 1.7 Рабочие гипотезы

**H1.** Безымянное lambda-представление с компактным prefix coding позволяет получить малый и однозначный wire-format с прямым структурным декодированием.

**H2.** Erased typing в стиле Hindley–Milner способен уменьшить повторяемый program payload, поскольку многие термы имеют выводимую principal type scheme [3,4], однако полный выигрыш зависит от пока неизвестной стоимости bootstrap алгоритма вывода.

**H3.** Небольшое число дополнительных семантических конструкций, например прямые натуральные числа и `Let`, способно уменьшить суммарный объём программ, несмотря на увеличение спецификации языка.

**H4.** Weak call-by-name может служить простой нормативной семантикой, а call-by-need sharing — наблюдательно эквивалентной оптимизацией реализации на тестируемом чистом фрагменте [9–11].

**H5.** Нельзя предполагать, что NEX будет компактнее сильно сжатых untyped lambda-кодировок вроде BLC на чистых lambda-термах; это должно измеряться [2].

**H6.** Одного program payload недостаточно для заявления о глобальном преимуществе; требуется receiver-neutral модель стоимости specification и bootstrap.

## 1.8 Научный вклад на текущей границе данных

Текущий вклад не является доказательством глобально минимального вычислительного языка. Он состоит в создании связанного исследовательского артефакта, включающего:

- нормативный типизированный Core и бинарный wire-format;
- reference implementation с исполняемой статической и динамической семантикой;
- language-neutral conformance-артефакты;
- явное отделение resource limits от корректности языка;
- замороженные benchmark-корпусы;
- воспроизводимые инструменты внутренних и внешних сравнений;
- модель total-information accounting, которая сохраняет неизвестные величины неизвестными;
- evidence-gated процесс принятия решений, где отрицательный результат способен блокировать преждевременное архитектурное утверждение.

# 2. Теоретическая база и связанные работы

## 2.1 Безымянные переменные и индексы de Bruijn

Имена переменных удобны человеку, но избыточны для канонического формата передачи. De Bruijn показал, что связанные переменные можно представлять числовыми ссылками, определяемыми структурой binder-ов [1; SRC-0001]. NEX использует этот принцип, но самостоятельно выбирает индексацию с нуля.

Практическое следствие: alpha-renaming не влияет на канонический терм. Различие между `lambda x. x` и `lambda y. y` исчезает из передаваемого представления, поскольку написание имени не несёт вычислительной информации.

## 2.2 Binary Lambda Calculus

Binary Lambda Calculus Джона Тромпа показывает, что lambda-термы с de Bruijn-подобными переменными можно кодировать компактным бинарным синтаксисом [2; SRC-0002]. Для NEX BLC играет две роли: подтверждает практичность компактной бинарной lambda-нотации и служит внешним baseline, способным опровергать слишком широкие заявления о компактности NEX.

NEX не копирует грамматику BLC. NEX добавляет статическую типизацию, `Let`, прямые натуральные числа и фиксированные примитивы, а BLC остаётся untyped. Поэтому сравнение Stage 4 ограничено общим чистым lambda-подмножеством, а BLC не обременяется скрытыми Church encodings встроенных возможностей NEX.

## 2.3 Hindley–Milner и principal type schemes

Полиморфная типовая дисциплина Milner даёт разрешимый вывод типов для полезного rank-1 let-полиморфного языка [3; SRC-0003]. Damas и Milner формализовали свойство principal type schemes для соответствующего функционального фрагмента [4; SRC-0004]. NEX использует эти идеи для восстановления типов по термам без передачи обычных type annotations в каноническом wire v0.1.

Это решение не объявляется глобально оптимальным. Результат Wells о неразрешимости общей typability/type checking в System F [7; SRC-0007] используется как теоретическая граница: расширение implicit polymorphism нельзя автоматически считать сохраняющим те же свойства выводимости. Поэтому v0.1 остаётся на ограниченной HM-точке.

## 2.4 Типизированная рекурсия и натуральные числа

Работа Plotkin по LCF/PCF даёт важный прецедент малого типизированного функционального языка с натуральными числами и fixed-point recursion [5; SRC-0005]. NEX аналогично сохраняет общую рекурсию через типизированный `fix`. Однако точный primitive set, суммы/произведения, wire-format и HM `Let` являются решениями NEX, а не переносом PCF.

## 2.5 Самоделитирующееся кодирование целых

Elias предложил универсальные семейства кодов для положительных целых чисел, включая gamma coding [6; SRC-0006]. NEX определяет `U(n)` как Elias gamma от `n + 1`, что позволяет самоделитирующе кодировать неотрицательные числа, de Bruijn indices и primitive IDs. Смещение на единицу и место `U(n)` в термовой грамматике специфичны для NEX.

## 2.6 Стратегии вычисления

Анализ Plotkin call-by-name и call-by-value показывает, что стратегия вычисления семантически значима [9; SRC-0011]. NEX выбирает weak call-by-name как нормативную reference strategy. Natural semantics Launchbury формализует sharing для lazy evaluation [10; SRC-0012], а Sestoft выводит реализационную машину для ленивых вычислений с sharing [11; SRC-0013]. Эти работы мотивируют эксперимент Stage 4: можно ли использовать call-by-need для уменьшения receiver work при сохранении наблюдаемого результата NEX.

Проект не принимает heap semantics Launchbury или machine state Sestoft как нормативную семантику NEX. Они используются как теоретический и реализационный прецедент.

## 2.7 Комбинаторные альтернативы и Jot

Малые базисы `S` и `K` исторически представляют альтернативный путь к вычислительной полноте [8; SRC-0009]. Материал Chris Barker по Iota/Jot даёт точное отображение `K`, `S` и application в Jot, использованное в эксперименте Stage 4 [12; SRC-0014]. При этом NEX не утверждает, что применённая детерминированная lambda-to-SK трансляция даёт кратчайшие Jot-программы.

## 2.8 Переносимое ядро и host embedding

Спецификация WebAssembly Core не является семантической основой NEX, но служит современным архитектурным примером разделения переносимого вычислительного ядра и среды embedding [13; SRC-0008]. NEX использует принцип разделения, но не заимствует конкретную stack-machine архитектуру, числовую модель, module system или memory model WebAssembly.

# 3. Методология исследования

## 3.1 Артефактно-экспериментальный метод

Проект следует циклу, в котором языковое утверждение не считается установленным только потому, что выглядит логичным или красивым:

```text
Problem
 -> Contract
 -> Invariant
 -> Failing test / executable example
 -> Implementation
 -> Verification
 -> Diff review
 -> Status checkpoint
```

Таким образом, implementation является одновременно инженерным результатом и исследовательским инструментом. Источником долговременной памяти считается репозиторий, а не история чатов.

## 3.2 Классы доказательств

Документация NEX разделяет пять классов:

1. **Установленный внешний результат** — подтверждён первичной литературой или официальной спецификацией.
2. **Проектное решение NEX** — выбор, зафиксированный в спецификации или Accepted ADR.
3. **Воспроизводимое измерение NEX** — результат, получаемый repository artifact и автоматической командой.
4. **Вывод из текущих данных** — интерпретация проекта, ограниченная условиями эксперимента.
5. **Открытая гипотеза / неизвестная величина** — не разрешена имеющимися доказательствами.

Это препятствует превращению повторяемого предположения в «факт» только из-за частоты его упоминания.

## 3.3 Воспроизводимость

Где возможно, prose-утверждения поддерживаются исполняемыми артефактами:

- golden/conformance vectors для wire;
- negative vectors для malformed input;
- scope/type conformance;
- evaluator conformance;
- unit/property/fuzz tests;
- frozen benchmark corpora;
- deterministic experiment CLI;
- clean-checkout GitHub Actions.

Итоговый Stage 4 report пересчитывается `reference/go/cmd/nexreport` и не копирует числа из Markdown.

## 3.4 Правило заморозки benchmark corpus

Benchmark-driven design подвержен post hoc подбору workload. Поэтому ADR-0010 требует считать corpus version неизменяемой после публикации сравнительных результатов. Новые задачи требуют новой версии. Сохранённый `corpus-v0.2.json`, где `factorial-5` превысил CBN transition budget, является примером сохранения неудобного результата вместо его незаметной замены.

## 3.5 Учёт полной информационной стоимости

Центральная модель:

```text
C = S + B + P
```

На текущем этапе:

- `P` — точный канонический wire cost для конкретного frozen corpus;
- `S` — receiver-neutral стоимость передачи спецификации, пока не представленная единственным принятым артефактом;
- `B` — receiver-neutral стоимость bootstrap, неизвестна;
- `R` — размер host/reference implementation, только proxy и никогда не подменяет `B`.

Невозможность сейчас вычислить `C` рассматривается как содержательный результат.

## 3.6 Границы эмпирических утверждений

Измерения считаются специфичными для corpus и translation, пока не доказано иное. Например, лидерство `Prim` по wire-cost относится к corpus v0.3, а не является теоремой о любых NEX-программах. BLC-сравнение относится только к чистому lambda-subset, а Jot-результат — к конкретной задокументированной трансляции.

# 4. Проект NEX-1 v0.1

## 4.1 Канонический язык термов

NEX-1 v0.1 содержит ровно шесть конструкторов:

```text
Term ::= Var(index)
       | Lam(body)
       | App(function, argument)
       | Let(value, body)
       | Nat(value)
       | Prim(id)
```

Имена переменных и human formatting намеренно исключены.

## 4.2 Система типов

```text
T ::= a | 1 | N | T -> T | T * T | T + T
S ::= forall a1 ... an. T
```

Статическая семантика использует rank-1 HM-style inference, включая fresh instantiation, let-generalization, унификацию и occurs check [3,4].

## 4.3 Базис примитивов

Core v0.1 фиксирует одиннадцать primitive IDs:

```text
0  fix
1  succ
2  pred
3  ifz
4  pair
5  fst
6  snd
7  inl
8  inr
9  case
10 unit
```

IDs 11–31 зарезервированы Core, profile-specific primitives начинаются с 32. Это отделяет универсальное вычислительное ядро от файлов, дисплея, сети, памяти и иных возможностей среды.

## 4.4 Wire-format

Неотрицательные целые кодируются `U(n) = EliasGamma(n+1)` [6]. Конструкторы используют prefix code:

```text
00   U(k)   Var(k)
01   T      Lam(T)
10   T T    App(T,T)
110  T T    Let(T,T)
1110 U(n)   Nat(n)
1111 U(p)   Prim(p)
```

Структура декодируется без текстовой токенизации.

## 4.5 Динамическая семантика

Нормативная стратегия — weak call-by-name. Аргументы и значения `Let` задерживаются, редукция под `Lam` не производится до применения. Примитивы форсируют аргументы выборочно: `ifz` вычисляет condition, но только выбранную ветвь; `pair` может сохранять delayed components; `case` выбирает соответствующую sum-ветвь. Общая рекурсия задаётся `fix`.

# 5. Stage 0 — исследовательская и архитектурная база

Stage 0 зафиксировал проект как исследовательский процесс, а не как неструктурированный эксперимент с языком. Были введены canonical English specification, обязательные русские зеркала для ключевых документов, архитектурная и доменная документация, workflow/testing, ADR governance, правило repository-as-memory и реестр первичных источников.

Сам Stage 0 не дал численного результата о компактности, но создал методологическое условие для последующих утверждений: rationale, rejected alternatives, источники и verification status должны быть долговременными и проверяемыми.

Реестр источников предпочитает первичные публикации, официальные стандарты и author-maintained references и требует указывать не только то, что проект использует, но и то, чего из источника делать нельзя.

**Вывод Stage 0.** До оптимизации минимального языка необходимо предотвратить silent semantic drift и ретроспективное переписывание архитектурной мотивации. ADR/source/status-механизм стал частью исследовательского метода.

# 6. Stage 1 — каноническое wire-основание

## 6.1 Цель

Stage 1 проверял RQ1 на уровне представления: можно ли однозначно переводить канонический NEX term в точную битовую последовательность и обратно с детерминированной классификацией ошибок.

## 6.2 Реализация

Go reference implementation получил arbitrary-precision `U(n)` encode/decode, структуру шести term constructors, canonical term codec, prefix/exact decoding API, malformed-input errors и resource limits, отделённые от синтаксической некорректности.

Это различие принципиально: математически корректный NEX natural или глубокий терм может превысить конечные ресурсы реализации, не становясь некорректным NEX. Поэтому resource-limit refusal классифицируется отдельно.

## 6.3 Conformance

Итоговый corpus Stage 1 содержал:

- 17 integer vectors;
- 12 term vectors;
- 15 invalid exact-input vectors.

Примеры:

```text
Var(0)                    001
Nat(0)                    11101
Prim(0)                   11111
Lam(Var(0))               01001
Lam(App(Prim(1),Var(0)))  01101111010001
```

Reference implementation прошёл formatting, vet, unit, conformance и fuzz/property verification в clean CI.

## 6.4 Вывод Stage 1

RQ1 поддерживается для реализованной wire grammar v0.1: канонические термы кодируются и декодируются детерминированно, а поведение проверяется исполняемыми conformance-векторами. Это ещё не formal proof, но уже значительно сильнее prose-only specification.

# 7. Stage 2 — статическая проверка и principal type inference

## 7.1 Проверка scope

Wire-validity не означает program-validity. Для zero-based de Bruijn `Var(k)` корректен только при наличии соответствующего enclosing binder. `Lam` увеличивает depth для body. `Let(value, body)` проверяет value в текущем окружении, а body — в окружении с новой binding.

Dedicated closed-scope validator отделяет binding errors от type errors.

## 7.2 Представление типов и substitutions

Stage 2 реализовал type variables, unit, natural, function, product, sum и quantified schemes, а также free-type-variable calculation, substitutions, substitution composition, fresh instantiation и environment-sensitive generalization.

Canonical renaming type variables позволяет сравнивать principal schemes разных implementation независимо от внутренних fresh IDs.

## 7.3 Unification и occurs check

Algorithm W требует унификации. Occurs check отвергает уравнения вида

```text
T0 = T0 -> N
```

и тем самым предотвращает бесконечные типы. Классический пример — self-application `lambda x. x x`, нетипизируемый в поддерживаемом HM-фрагменте.

## 7.4 Primitive schemes и inference

Одна таблица Core primitives хранит ID, name, arity и type scheme. `InferClosed` выполняет scope validation, primitive validation и principal inference для всех шести конструкторов.

Conformance включает положительные principal types и ошибки out-of-scope, unknown primitive, type mismatch и occurs check.

## 7.5 Решение по type annotations

NEX-1 v0.1 не передаёт обычные term-level type annotations. Это проектное решение, а не доказанная глобальная оптимальность. HM теоретически позволяет principal inference [3,4], но исследовательская цель — total information, а не эстетика типовой системы. Поэтому ADR-0007 сохраняет erased types в v0.1 и откладывает сравнение с explicit/certified variants.

## 7.6 Вывод Stage 2

RQ2 функционально поддерживается: reference implementation восстанавливает principal type schemes закрытого Core без ordinary type annotations. Но вопрос минимизации `S+B+P` остаётся открытым и возвращается в Stage 4.

# 8. Stage 3 — динамическая семантика и evaluator

## 8.1 Модель вычисления

Stage 3 определил environment-based weak CBN evaluator с closures и delayed arguments. Это избегает постоянной syntactic substitution и естественно сочетается с de Bruijn environments.

## 8.2 Проверка нестрогости

Проверялись не только arithmetic results, но и сама laziness. Программы, эквивалентные

```text
(lambda x. 7) divergingTerm
ifz 0 42 divergingTerm
fst (pair 1 divergingTerm)
```

должны возвращать `7`, `42` и `1`, не вычисляя ненужную ветвь [9].

## 8.3 Curried primitives и fixed point

Primitives поддерживают partial application. `fix` обеспечивает general recursion. Поскольку divergence допустима по смыслу, evaluator fuel/depth являются implementation controls, а не правилами корректности языка.

## 8.4 Conformance

`conformance/eval-v0.1.json` задаёт language-neutral observations. Fuzz/property tests проверяют deterministic observable behavior успешных вычислений. Нормативные English/Russian dynamic-semantics sections были синхронизированы.

## 8.5 Вывод Stage 3

RQ3 частично поддерживается ещё до оптимизации: простая weak CBN semantics исполняема и conformance-tested. Вопрос, можно ли sharing-реализацией уменьшить receiver work при сохранении результата, переносится в Stage 4.

# 9. Stage 4 — эмпирическая проверка и benchmark

## 9.1 Measurement contract и corpus

Stage 4 намеренно зафиксировал правила измерений до оптимизации. Corpus v0.1 содержит 10 foundation programs. Corpus v0.2 сохранён как отрицательная/resource checkpoint: `factorial-5` превысил default non-memoizing CBN budget в 1 000 000 transitions. Corpus v0.3 — принятый расширенный corpus из 17 программ.

В нём представлены pure lambda, arithmetic/control primitives, pairs, sums, polymorphic `Let`, recursion, multiplication, factorial, Fibonacci, небольшой recognizer и повторное использование дорогого let-binding.

## 9.2 Aggregate wire profile

| Метрика | Значение |
|---|---:|
| Программ | 17 |
| Wire bits | 1371 |
| AST nodes | 345 |

Распределение:

| Конструктор | Биты | Доля |
|---|---:|---:|
| `Prim` | 460 | 33,6% |
| `Var` | 286 | 20,9% |
| `App` | 264 | 19,3% |
| `Nat` | 244 | 17,8% |
| `Lam` | 84 | 6,1% |
| `Let` | 33 | 2,4% |

Ранняя гипотеза о доминировании `App` не подтверждается этим corpus. Самый большой вклад дают primitive references. Вывод ограничен corpus v0.3: это основание приоритизировать primitive/profile encoding в будущих опытах, но не универсальная теорема.

## 9.3 `Let` против duplication

Для закрытого payload в 5 бит:

| Повторы | Эффект `Let` относительно дублирования |
|---:|---:|
| 2 | +4 бита |
| 3 | +2 бита |
| 4 | ничья |
| 8 | −8 бит |

Для протестированного 14-битного payload уже два повторения экономят 5 бит. Следовательно, отвергаются обе крайности: `Let` не всегда лучше и не всегда хуже. Он имеет измеримую break-even point, зависящую от размера payload и количества повторений.

**Решение:** сохранить `Let` в v0.1.

## 9.4 Прямой `Nat` против repeated `succ`

`Nat(n)` сравнивался с простым построением числа повторным `succ` от нуля. Для `n=0` формы равны. Для всех протестированных значений `1..255` прямой literal меньше. На крайней точке:

```text
Nat(255)          21 бит
succ-chain(255) 2300 бит
экономия         2279 бит
```

Это не доказывает глобальную оптимальность Elias-gamma `Nat`, но сильно опровергает идею удалить direct naturals ради проверенной successor construction.

**Решение:** сохранить direct `Nat` в v0.1.

## 9.5 Erased HM против principal root type payload

Не-нормативный hybrid envelope добавлял только inferred closed principal top-level type scheme, оставляя canonical term неизменным.

```text
erased NEX terms       1371 бит
root type payload       134 бита
hybrid total           1505 бит
overhead               +9,77%
```

Overhead сильно зависит от workload. Маленькие полиморфные функции платят дорого: identity +240%, constant +222,2%, composition +200%. Большинство крупных программ с типом `N` требуют только 4 type bits; у factorial-4 это около +1,67%.

Эксперимент измеряет только `Delta P`. Principal root type не заменяет внутренние typing judgments, и alternative receiver checker/bootstrap не реализован. Поэтому total-cost comparison erased HM и explicit/certified design пока не решён.

**Решение:** сохранить erased HM в v0.1 и отложить глобальный redesign до появления реального checker/bootstrap evidence.

## 9.6 External/structural baselines

### 9.6.1 Binary Lambda Calculus

BLC сравнивался только на одинаковом pure-lambda subset (`identity`, `constant`, `composition`), чтобы не вводить Church encodings встроенных `Nat/Prim`.

| Программа | NEX | BLC |
|---|---:|---:|
| identity | 5 | 4 |
| constant | 9 | 7 |
| composition | 23 | 19 |
| **Итого** | **37** | **30** |

BLC на 7 бит меньше на этом общем фрагменте. Тем самым опровергается blanket-утверждение, что текущая lambda-кодировка NEX всегда компактнее BLC [2]. Но это не доказывает superiority BLC для полного вычислительного базиса NEX.

### 9.6.2 Jot через deterministic SK translation

Тот же lambda-subset дал 288 бит для задокументированной цепочки lambda→SK→Jot против 37 у NEX. Mapping Jot основан на Barker [12], но bracket abstraction — проектный выбор, а не shortest-program search. Результат относится только к этой воспроизводимой трансляции.

### 9.6.3 Tiny postfix baseline

Проектный 3-битный postfix structural encoding применялся ко всем 17 программам и переиспользовал NEX integer/primitive conventions:

```text
NEX canonical wire   1371 бит
tiny postfix stack   1529 бит
разница               +158 бит (+11,52%)
```

Это поддерживает узкое утверждение, что выбранная NEX tree encoding меньше выбранной postfix encoding на corpus v0.3. Это не independent `S+B+P` comparison.

## 9.7 Call-by-name против call-by-need

Был реализован отдельный экспериментальный call-by-need evaluator с memoization. Normative v0.1 semantics осталась weak CBN. Все программы должны были дать одинаковый observable WHNF.

Все 17 программ совпали.

```text
CBN transitions             226151
call-by-need transitions      2484
экономия                    223667
снижение                     98,90%
memo hits                       237
программ с меньшим числом transitions 6/17
```

Примеры:

```text
countdown-5            127 -> 92
multiplication-3-4     446 -> 301
factorial-4         209315 -> 895
fibonacci-5           7424 -> 512
let-reuse-expensive    8710 -> 560
```

Aggregate dominated тяжёлыми recursive/reused computations. Большинство малых программ не получают никакого reduction. Поэтому корректный вывод: sharing способен устранять катастрофическое повторное вычисление в важных классах workload, но нельзя утверждать, что call-by-need «всегда быстрее на 98,90%».

Эти transitions являются Go-reference metrics, не portable Core cost и не частью `C`. Call-by-need может увеличить bootstrap/runtime machinery.

**Решение:** оставить weak CBN нормативным и разрешить call-by-need как оптимизацию при сохранении observables.

## 9.8 Total-information accounting

```text
P exact canonical program cost       1371 бит
canonical English spec Markdown     23440 UTF-8 байт
raw Markdown text proxy            187520 бит
selected Go reference Core         43013 UTF-8 байт
B receiver-neutral bootstrap       неизвестен
C total                             численно не вычисляется
```

Markdown value прозрачен, но не принимается как `S`, поскольку предполагает English, UTF-8, Markdown и земные текстовые conventions. Go source — это `R`, не `B`: он предполагает Go syntax, compiler/runtime, machine memory и множество других разделяемых conventions. Подмена proxy ответила бы на исследовательский вопрос предположением.

**Решение:** total-cost superiority остаётся нерешённым; unknown `B` никогда не считается нулём.

## 9.9 Reproducible report и decision gate

`reference/go/cmd/nexreport` пересчитывает основные Stage 4 metrics из frozen corpus и функций experiment/reference. Decision gate зафиксирован ADR-0011.

Финальный clean-checkout Stage 4 verification run на завершённой ветке: GitHub Actions `35373798219`, success.

# 10. Обсуждение и ответы на исследовательские вопросы

## 10.1 RQ1 — детерминированный wire-format

**Текущий ответ: поддерживается для NEX-1 v0.1.** Canonical term grammar, self-delimiting integers, exact/prefix APIs, error taxonomy, vectors и automated round-trip/fuzz evidence дают работоспособный wire layer. Formal proof и independent decoder пока отсутствуют.

## 10.2 RQ2 — восстановление типов без ordinary annotations

**Текущий ответ: функционально поддерживается, глобально не решён.** Reference implementation выводит principal schemes. Stage 4 показал +9,77% `P` для одного hybrid root-type envelope, но не реализовал альтернативный bootstrap. Erased HM остаётся обоснованным решением v0.1, но не доказанным total-cost optimum.

## 10.3 RQ3 — простая семантика и эффективная реализация

**Текущий ответ: сильно поддерживается на тестируемом corpus.** Weak CBN задаёт простую semantics; experimental call-by-need сохранил observables и резко уменьшил repeated work на части recursive workloads. Стоимость дополнительного bootstrap не измерена.

## 10.4 RQ4 — dominant constructors и оправданность `Let`/`Nat`

**Текущий ответ:** `Prim` доминирует на этом corpus; `Let` и direct `Nat` оправданы относительно протестированных альтернатив. Это опровергает упрощённую идею «меньше constructors всегда лучше».

## 10.5 RQ5 — сравнение с alternatives

**Текущий ответ: смешанный и потому научно полезный.** BLC меньше на identical pure-lambda subset. NEX меньше выбранного tiny postfix structural baseline на полном corpus. Jot translation больше, но не является shortest-program result. Победителя по total cost назвать нельзя.

## 10.6 RQ6 — численный total information cost

**Текущий ответ: нет.** `P` известен точно для frozen corpora, но receiver-neutral `S` и особенно `B` отсутствуют. После Stage 4 это главный нерешённый вопрос.

# 11. Ограничения и угрозы валидности

## 11.1 Размер и репрезентативность corpus

v0.3 содержит 17 программ. Он покрывает разные features, но не представляет все возможные распределения реального ПО. Constructor percentages являются corpus-specific.

## 11.2 Bias ручного построения и трансляции

Часть термов и baseline translation построена вручную, а не независимыми optimizing compilers. Классификация translation снижает риск, но не устраняет его. В дальнейшем нужны common-source translations и independently optimized variants.

## 11.3 Одна полная реализация

Go пока единственная complete reference implementation. Ошибка понимания, общая для spec и code, может пройти внутренние tests. Нужна независимая реализация по specification + conformance.

## 11.4 Runtime counters implementation-specific

Transition/depth описывают Go evaluators и не являются architecture-neutral units of computation.

## 11.5 Неполный explicit-type experiment

Hybrid передаёт только principal root type, но не full typed wire/proof object/receiver checker. Он не позволяет измерить bootstrap savings.

## 11.6 Ограниченность external baselines

BLC comparison узкий; tiny stack reuse NEX conventions; Jot зависит от одной bracket abstraction. Это защищает от скрытых assumptions, но ограничивает выводы.

## 11.7 Неизвестные receiver-neutral `S` и `B`

Главный gap относительно исходной цели: specification и bootstrap пока не представлены receiver-neutral artifacts. Поэтому total cost incomplete by construction.

## 11.8 Отсутствие formal proof

Fuzz/conformance/CI являются эмпирическими доказательствами, а не machine-checked proof codec/type/evaluator correctness.

# 12. Научный вклад на текущем этапе

Работа предоставляет:

1. конкретный architecture-neutral typed Core с canonical binary representation;
2. исполняемое разделение wire-validity, scope-validity, type-validity и resource refusal;
3. language-neutral conformance corpora для wire/static/dynamic semantics;
4. evidence-gated methodology с freeze benchmarks до оптимизации;
5. exact constructor-level wire attribution;
6. measured break-even для `Let` и сильное evidence за direct `Nat` против repeated `succ`;
7. quantified first experiment erased vs transmitted root type;
8. controlled comparisons с BLC, Jot translation и structural stack baseline;
9. observational CBN/CBNeed experiment с крупной runtime savings на выбранных workloads;
10. accounting model, запрещающую подменять receiver-neutral bootstrap размером host source;
11. living dissertation process для накопления положительных, отрицательных и нерешённых результатов.

# 13. Направления дальнейшего исследования

## 13.1 Независимая conformance implementation

Следующий крупный шаг — вторая реализация, построенная по public specification и conformance artifacts, а не переводом Go code. Agreement проверит, действительно ли specification однозначно определяет поведение.

## 13.2 Receiver-neutral bootstrap artifact

Главная неизвестная — `B`. Необходимо определить, какую информацию должен получить receiver, чтобы восстановить decode, validate, type-check и evaluate без предположения о Go, обычном CPU, ASCII/UTF-8, files или OS.

Сам bootstrap должен получить transmission representation, иначе его нельзя честно включить в `C`.

## 13.3 Receiver-neutral specification cost

Markdown не является `S`. Требуется исследование self-describing mathematical/specification bootstrap: как вводить bit parsing, binding, typing и evaluation из более слабых общих assumptions.

## 13.4 Primitive-reference encoding

Так как `Prim` — крупнейшая wire-category corpus v0.3, будущие compactness experiments должны исследовать primitive ID/profile encoding раньше, чем менять `App` на основании интуиции. Incompatible changes требуют новой Core version и ADR.

## 13.5 Полноценные typing alternatives

Meaningful erased-vs-explicit comparison требует alternative verifier/checker и bootstrap accounting, а не только передачи root type.

## 13.6 Более широкие corpora и common-source normalization

Future corpora должны включать более крупные structural programs и common-source translations для честного сравнения нескольких target encoding. Freeze/version discipline сохраняется.

## 13.7 Formal verification

Decoder prefix properties, substitution/unification invariants и evaluator equivalence являются кандидатами для theorem prover/proof assistant после стабилизации executable design.

# 14. Заключение

Исследование началось с простой идеи: если существующие языки программирования создавались для людей и известных машин, какое вычислительное представление следует использовать, когда нельзя предполагать ни то, ни другое?

Результаты показывают, что ответ нельзя свести к самому короткому синтаксису. NEX-1 v0.1 демонстрирует, что небольшой типизированный lambda-core может иметь компактную каноническую бинарную форму, выводить principal types без ordinary annotations и выполняться с явно нестрогой семантикой. Ещё важнее то, что поэтапная реализация делает эти утверждения исполняемыми и фальсифицируемыми.

Эмпирические результаты не поддерживают упрощённую историю успеха. Direct naturals сильно оправданы против tested successor construction, а `Let` имеет реальную break-even point. Одновременно BLC компактнее на measured pure-lambda subset. Call-by-need может на порядки уменьшить repeated evaluation work в некоторых программах, но это само по себе ничего не говорит о communication cost. `Prim`, а не `App`, оказался крупнейшим measured wire contributor. И главная целевая функция `C = S + B + P` остаётся нерешённой, потому что receiver-neutral bootstrap ещё не определён.

Это не недостатки, которые следует скрыть. Именно они являются главным результатом текущего научного этапа. Проект перешёл от интуиции о «маленьком языке» к воспроизводимой экспериментальной системе, в которой гипотезы могут подтверждаться, опровергаться или уточняться данными. Следующий решающий вопрос уже не в том, можно ли сократить один AST-prefix на бит, а в том, сможет ли независимый receiver восстановить систему по действительно receiver-neutral specification/bootstrap и сколько такой bootstrap будет стоить.

# Словарь терминов

**ABI (Application Binary Interface)** — соглашения бинарного взаимодействия компонентов с платформой.

**Alpha-equivalence** — эквивалентность lambda-термов, различающихся только именами связанных переменных.

**Architecture-neutral** — не зависящий от конкретной ISA, размера слова, ABI, OS или runtime host-языка.

**AST (Abstract Syntax Tree)** — структурное представление программного терма.

**Binder** — конструкция, вводящая связанную переменную; в NEX это `Lam` и body-часть `Let`.

**Binary Lambda Calculus (BLC)** — компактное бинарное представление untyped lambda terms Джона Тромпа [2].

**Bootstrap (`B`)** — receiver-neutral информация, необходимая для реализации механизма обработки NEX. Сейчас неизвестна и не равна размеру Go source.

**Call-by-name (CBN)** — нестрогая стратегия, где аргумент не вычисляется до использования и может вычисляться повторно [9].

**Call-by-need** — lazy evaluation с sharing/memoization, устраняющая повторное вычисление одного thunk [10,11]. В NEX пока experimental implementation strategy.

**Canonical representation** — уникальная проектная структурная/wire форма для conformance и измерений.

**Conformance vector** — language-neutral input/expected-output artifact для проверки реализации.

**de Bruijn index** — числовая ссылка на binder depth вместо имени переменной [1].

**Erased typing** — type information отсутствует в ordinary term wire и восстанавливается inference.

**Hindley–Milner (HM)** — rank-1 polymorphic type inference discipline, используемая NEX [3,4].

**Occurs check** — проверка, запрещающая унифицировать type variable с типом, содержащим саму эту variable.

**Principal type scheme** — наиболее общий тип HM-терма, из которого получаются остальные допустимые instantiations [4].

**Primitive (`Prim`)** — фиксированная Core operation с numeric ID, например `succ`, `ifz`, `pair`.

**Receiver-neutral** — не требующий непереданных земных implementation conventions.

**Resource refusal** — отказ реализации из-за конечных лимитов, отличающийся от malformed syntax, type invalidity и доказанной divergence.

**Specification cost (`S`)** — информация, необходимая для передачи правил самой вычислительной системы. Accepted receiver-neutral scalar пока отсутствует.

**Thunk** — delayed computation, концептуально term + environment.

**Total information cost (`C`)** — исследовательская целевая функция `C = S + B + P`.

**Transmitted-program cost (`P`)** — точное число canonical wire bits для заданного набора программ.

**Unification** — решение ограничений равенства типов через substitutions.

**Weak-head normal form (WHNF)** — результат, вычисленный только до раскрытия внешнего constructor/function/value, без полной рекурсивной нормализации содержимого.

**Wire format** — каноническое битовое представление NEX-термов при передаче.
