# Архитектура

Русский перевод архитектурного обзора NEX.

> Нормативной является английская версия `docs/ARCHITECTURE.md`. При расхождении формулировок приоритет имеет английский документ до синхронизации перевода.

Этот документ описывает текущую логическую архитектуру проекта NEX. Это живое представление принятых ADR и спецификации; оно не заменяет их.

## Уровни

```text
Human / machine frontend syntax
            |
            v
      Canonical NEX terms
            |
     +------+------+
     |             |
     v             v
 Type inference   Wire codec
     |             |
     +------+------+
            |
            v
        Core evaluator
            |
            v
   Optional execution profiles
            |
            v
      Host / target machine
```

Иными словами:

```text
человеческий или машинный frontend
            ↓
канонические NEX-термы
            ↓
    вывод типов / wire codec
            ↓
       Core evaluator
            ↓
  дополнительные execution profiles
            ↓
      host / целевая машина
```

## Модель Core

NEX-1 Core v0.1 имеет шесть канонических конструкторов термов:

```text
Var
Lam
App
Let
Nat
Prim
```

Система типов предоставляет натуральные числа, unit, функции, произведения, суммы и rank-1 let-полиморфизм.

Общая рекурсия задаётся явно через примитив `fix`.

## Границы модулей reference implementation

Первая реализация должна быть разбита на модули с узкими контрактами.

### `term`

Владеет каноническим in-memory представлением термов и правилами области видимости de Bruijn.

Не должен ничего знать о разборе человеко-ориентированного исходного языка.

### `wire`

Владеет каноническим битовым кодированием/декодированием и самоделимитирующимся кодом натуральных чисел.

Контракт:

```text
encode : Term -> Bits
decode : Bits -> Result<Term, DecodeError>
```

Decoder должен отвергать некорректные представления в соответствии со спецификацией.

### `types`

Владеет термами типов, схемами типов, подстановками, операциями над свободными переменными типов и унификацией.

### `infer`

Владеет выводом типов в стиле Algorithm W для NEX-термов и окружением типов примитивов.

Контракт:

```text
infer : Term -> Result<TypeScheme, TypeError>
```

### `eval`

Владеет эталонной семантикой вычисления.

Он должен реализовывать специфицированное наблюдаемое поведение, а не произвольную оптимизированную модель.

### `primitives`

Владеет стабильной таблицей Core primitive ID, схемами типов и правилами редукции примитивов.

Концептуально должна существовать одна авторитетная таблица примитивов; вывод типов и evaluator не должны разойтись на две независимо поддерживаемые несовместимые версии.

### `conformance`

Владеет нормативными/golden vectors, проверяющими decode, encode, вывод типов, отказ на ошибочных данных и вычисление.

### `bench`

Владеет воспроизводимыми измерениями. Benchmark-результаты нельзя смешивать с утверждениями о корректности/conformance.

## Направление зависимостей

Предпочтительное направление:

```text
term <- wire
term <- infer <- types
term <- eval
infer <- primitives -> eval
conformance -> all public contracts
bench -> public contracts
```

Следует избегать циклических зависимостей между evaluator, type inference и wire codec.

## Что не входит в первую reference implementation

Первая реализация не должна добавлять без отдельного ADR:

- C-like или Rust-like frontend;
- генерацию нативного машинного кода;
- модель изменяемой host-памяти;
- привязки к операционной системе;
- рекурсивные алгебраические типы;
- линейные типы;
- DAG/content-addressed transport;
- оптимизирующие проходы.

Все эти направления могут оказаться полезными позже, но сейчас они ослабят первый feedback loop. Сначала необходимо доказать реализуемость Core-спецификации.
