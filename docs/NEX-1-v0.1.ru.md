# NEX-1 v0.1

**Статус:** Черновик спецификации  
**Версия:** 0.1  
**Дата:** 2026-09-18

> Это информативный русский перевод. Нормативной является английская версия `docs/NEX-1-v0.1.md`. Если формулировки расходятся, до синхронизации перевода приоритет имеет английская спецификация.

NEX-1 — минимальный, архитектурно-независимый, статически типизированный язык, предназначенный для компактной передачи программ между системами, у которых нет общего языка программирования, архитектуры процессора, ABI, операционной системы или текстовой нотации.

Цель дизайна — не минимизировать только интерпретатор. NEX-1 стремится минимизировать совокупную информационную стоимость:

```text
cost = specification + bootstrap implementation + transmitted programs
```

Поэтому Core сохраняет lambda-абстракцию и аппликацию вместо сведения любой программы к минимальному набору комбинаторов, если такое сведение увеличивает размер программ.

---

## 1. Принципы дизайна

NEX-1 Core следует этим правилам:

1. Программы имеют каноническое бинарное представление.
2. Имена связанных переменных никогда не передаются.
3. Программы статически типизируются до выполнения.
4. Большинство аннотаций типов не передаётся; типы выводятся.
5. Core не зависит от размера машинного слова, порядка байтов, указателей, операционных систем, файлов, сетей, дисплеев и кодировок символов.
6. Общая рекурсия задаётся явно и является частью Core.
7. Взаимодействие с машиной определяется дополнительными профилями, а не самим Core-языком.
8. Получатель должен иметь возможность отвергнуть некорректную или плохо типизированную программу до её выполнения.

Математическая основа — lambda-исчисление без аннотаций с индексами de Bruijn, rank-1 let-полиморфизмом в стиле Hindley-Milner, натуральными числами, алгебраическими типами произведения/суммы и типизированным примитивом фиксированной точки.

## 2. Нотация

В документе используются читаемые имена вроде `Lam`, `App`, `fix` и `succ`. Эти имена существуют только в документации. Они не являются частью канонического wire-представления.

Ключевые слова **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** и **MAY** имеют нормативный смысл, как в английской спецификации.

## 3. Типы

Грамматика Core-типов:

```text
T ::= a
    | 1
    | N
    | T -> T
    | T * T
    | T + T
```

где:

- `a` — переменная типа;
- `1` — unit-тип;
- `N` — математический тип натуральных чисел произвольной точности;
- `A -> B` — тип функции;
- `A * B` — тип произведения;
- `A + B` — тип суммы.

Схемы типов:

```text
S ::= forall a1 ... an. T
```

Универсальная квантификация существует только в системе типов. `forall` не является конструктором терма и не передаётся в обычных термах.

### 3.1 Примеры

```text
N -> N
N * N
1 + N
forall a. a -> a
forall a b. a * b -> b * a
```

`1 + A` можно использовать как optional-значение без введения отдельного типа `Option`.

---

## 4. Core-термы

Программа NEX-1 Core использует ровно шесть конструкторов термов:

```text
Term ::= Var(index)
       | Lam(body)
       | App(function, argument)
       | Let(value, body)
       | Nat(value)
       | Prim(id)
```

Никаких других конструкторов термов в NEX-1 Core v0.1 нет.

В частности, Core не имеет отдельных синтаксических узлов для:

```text
if, while, for, return, struct, enum, pair, switch,
+, -, *, class, method, exception, pointer, module
```

Эти понятия выражаются через примитивы, функции, библиотеки или будущие профили.

---

## 5. Переменные и индексы de Bruijn

NEX-1 использует индексы de Bruijn с нуля.

Внутри binder:

```text
0 = ближайший внешний binder
1 = следующий внешний binder
2 = следующий внешний binder
...
```

Читаемое выражение:

```text
\x -> \y -> x
```

Каноническое дерево:

```text
Lam(
  Lam(
    Var(1)
  )
)
```

Читаемое выражение:

```text
\x -> \y -> y
```

Каноническое дерево:

```text
Lam(
  Lam(
    Var(0)
  )
)
```

Следовательно, имена переменных никогда не требуются в wire-представлении.

Программа верхнего уровня NEX-1 MUST быть замкнутой: каждый `Var(k)` MUST ссылаться на внешний `Lam` или `Let` binder.

---

## 6. Lambda-абстракция

`Lam(body)` вводит одно связанное значение. Внутри `body` это значение представлено как `Var(0)`.

Читаемая форма:

```text
\x -> x
```

Каноническая форма:

```text
Lam(Var(0))
```

Её главный тип:

```text
forall a. a -> a
```

---

## 7. Аппликация

`App(f, x)` применяет `f` к `x`.

Читаемая форма:

```text
f x
```

Несколько аппликаций ассоциируются влево:

```text
f a b c
```

означает:

```text
(((f a) b) c)
```

---

## 8. Let-связывание

`Let(value, body)` означает полиморфное let-связывание.

Читаемая форма:

```text
let x = value in body
```

Внутри `body` переменная `x` представляется как `Var(0)`.

`Let` является отдельным конструктором AST, потому что в Hindley-Milner обобщение типов происходит в let-связываниях. Замена любого `let x = a in b` на `App(Lam(b), a)` изменила бы поведение типизации.

---

## 9. Натуральные числа

`Nat(n)` содержит натуральное число:

```text
n >= 0
```

`N` имеет произвольную математическую точность. Он не определяется как host `int`, `uint32`, `uint64` или машинное слово.

Большие значения кодируются непосредственно в бинарном виде при помощи wire-кода целого числа, описанного ниже; NEX-1 не использует числа Чёрча как каноническое числовое представление.

---

## 10. Таблица Core-примитивов

NEX-1 Core v0.1 резервирует primitive ID `0..10` в точности следующим образом.

| ID | Имя | Схема типа |
|---:|---|---|
| 0 | `fix` | `forall a. (a -> a) -> a` |
| 1 | `succ` | `N -> N` |
| 2 | `pred` | `N -> N` |
| 3 | `ifz` | `forall a. N -> a -> a -> a` |
| 4 | `pair` | `forall a b. a -> b -> a * b` |
| 5 | `fst` | `forall a b. a * b -> a` |
| 6 | `snd` | `forall a b. a * b -> b` |
| 7 | `inl` | `forall a b. a -> a + b` |
| 8 | `inr` | `forall a b. b -> a + b` |
| 9 | `case` | `forall a b c. (a + b) -> (a -> c) -> (b -> c) -> c` |
| 10 | `unit` | `1` |

Primitive ID `11..31` зарезервированы для будущих ревизий Core и MUST NOT назначаться внешними профилями.

Профильные примитивы MUST использовать ID `>= 32`.

## 11. Семантика примитивов

### 11.1 Натуральные числа

```text
succ n       -> n + 1
pred 0       -> 0
pred (n + 1) -> n
```

### 11.2 Ветвление по нулю

```text
ifz 0       z s -> z
ifz (n + 1) z s -> s
```

Вычисляться обязана только выбранная ветвь.

### 11.3 Произведения

Концептуально `pair a b` является значением произведения.

```text
fst (pair a b) -> a
snd (pair a b) -> b
```

### 11.4 Суммы

Концептуально:

```text
inl a : A + B
inr b : A + B
```

Редукция:

```text
case (inl a) f g -> f a
case (inr b) f g -> g b
```

### 11.5 Фиксированная точка

```text
fix f -> f (fix f)
```

`fix` обеспечивает общую рекурсию и поэтому допускает не завершающиеся программы.

---

## 12. Стратегия вычисления

Эталонная семантика — **weak call-by-name**.

Аргумент функции подставляется без предварительного вычисления.

Основное beta-правило концептуально выглядит так:

```text
App(Lam(body), argument) -> body[0 := argument]
```

Реализации SHOULD избегать буквальной подстановки, подверженной захвату переменных, и MAY использовать окружения, closures, explicit substitutions, graph reduction или call-by-need.

Реализация MAY использовать memoization в стиле call-by-need при условии, что наблюдаемый Core-результат совпадает с эталонной семантикой.

Вычисление не выполняет редукцию внутри `Lam`, пока lambda не применяется.

---

## 13. Типизация

Совместимый получатель MUST выполнить проверку типов декодированного замкнутого терма до запуска.

NEX-1 v0.1 использует rank-1 let-полиморфизм в стиле Hindley-Milner.

### 13.1 Переменная

Для `Var(k)` берётся `k`-я привязка из типового окружения, после чего её схема типа инстанцируется свежими переменными типов.

### 13.2 Lambda

Для:

```text
Lam(body)
```

новому binder назначается свежий монотип `A`. Если:

```text
body : B
```

то:

```text
Lam(body) : A -> B
```

### 13.3 Аппликация

Для:

```text
App(f, x)
```

выводятся:

```text
f : A
x : B
```

создаётся свежая переменная типа `C`, затем выполняется унификация:

```text
A ~ B -> C
```

Если унификация невозможна, терм плохо типизирован.

### 13.4 Let

Для:

```text
Let(value, body)
```

1. вывести монотип `value`;
2. применить текущую подстановку;
3. обобщить переменные типов, которые не свободны во внешнем окружении;
4. добавить полученную схему типа как ближайшую привязку для `body`;
5. вывести тип `body`.

### 13.5 Примитив

`Prim(id)` инстанцируется из схемы типа соответствующего примитива.

Неизвестный primitive ID недопустим, если он не принадлежит явно выбранному внешнему профилю.

### 13.6 Occurs check

Унификация MUST выполнять occurs check. Переменная типа MUST NOT унифицироваться с типом, содержащим саму эту переменную.

## 14. Валидность программы

Core payload считается корректным только если одновременно выполняются все условия:

1. битовый поток декодируется ровно в один полный терм;
2. после него не остаётся лишних битов терма, не являющихся padding;
3. каждый индекс de Bruijn находится в области видимости;
4. каждый Core primitive ID определён;
5. вывод типов завершается успешно;
6. терм верхнего уровня замкнут.

Завершение вычисления не требуется. Корректная программа NEX-1 может расходиться, поскольку `fix` обеспечивает общую рекурсию.

## 15. Самоделимитирующийся код натурального числа U(n)

NEX-1 использует самоделимитирующийся код `U(n)` для неотрицательных целых чисел.

Пусть:

```text
m = n + 1
```

Запишем `m` в обычном двоичном виде без ведущих нулей. Пусть длина записи равна `L` бит.

Тогда:

```text
U(n) = (L - 1 нулевых битов) + binary(m)
```

Примеры:

| n | U(n) |
|---:|---|
| 0 | `1` |
| 1 | `010` |
| 2 | `011` |
| 3 | `00100` |
| 4 | `00101` |
| 5 | `00110` |
| 6 | `00111` |
| 7 | `0001000` |

Это эквивалент Elias gamma coding для `n + 1`.

---

## 16. Каноническое wire-кодирование

Core-терм рекурсивно кодируется следующей префиксной грамматикой:

```text
00   U(k)   Var(k)
01   T      Lam(T)
10   T T    App(T, T)
110  T T    Let(T, T)
1110 U(n)   Nat(n)
1111 U(p)   Prim(p)
```

Префиксы конструкторов prefix-free:

```text
00
01
10
110
1110
1111
```

Поэтому не требуются скобки, разделители, идентификаторы, пробелы или текстовые ключевые слова.

Канонический Core-объект — это **битовая строка**, а не строка байтов.

---

## 17. Упаковка в байты

Если битовую строку NEX необходимо хранить в октетах:

1. биты упаковываются от старшего бита к младшему внутри каждого октета;
2. последний октет при необходимости дополняется справа нулевыми битами;
3. транспортный контейнер MUST хранить точную длину полезной битовой строки, поскольку padding-нули не являются частью Core-терма.

Сам транспортный контейнер находится вне NEX-1 Core v0.1.

## 18. Примеры кодирования

### 18.1 Identity

Читаемая форма:

```text
\x -> x
```

AST:

```text
Lam(Var(0))
```

Кодирование:

```text
Lam     = 01
Var     = 00
U(0)    = 1
```

Результат:

```text
01001
```

Длина: **5 бит**.

Главный тип:

```text
forall a. a -> a
```

Тип выводится и не передаётся вместе с термом.

### 18.2 Функция successor

Читаемая форма:

```text
\x -> succ x
```

AST:

```text
Lam(
  App(
    Prim(1),
    Var(0)
  )
)
```

Кодирование:

```text
01           Lam
10           App
1111 010     Prim(1)
00 1         Var(0)
```

Результат:

```text
01101111010001
```

Длина: **14 бит**.

Выведенный тип:

```text
N -> N
```

## 19. Производные функции

Следующие примеры используют читаемую нотацию и не вводят дополнительный синтаксис Core.

### 19.1 Сложение

```text
add =
  fix (\self ->
    \a ->
      \b ->
        ifz b
          a
          (succ (self a (pred b))))
```

Тип:

```text
N -> N -> N
```

### 19.2 Умножение

```text
mul =
  fix (\self ->
    \a ->
      \b ->
        ifz b
          0
          (add a (self a (pred b))))
```

Тип:

```text
N -> N -> N
```

### 19.3 Факториал

```text
fact =
  fix (\self ->
    \n ->
      ifz n
        1
        (mul n (self (pred n))))
```

Тип:

```text
N -> N
```

### 19.4 Swap

```text
swap = \p -> pair (snd p) (fst p)
```

Главный тип:

```text
forall a b. a * b -> b * a
```

## 20. Optional-значения

Обычное optional-значение можно представить как:

```text
Option A = 1 + A
```

Читаемые соглашения:

```text
None   = inl unit
Some x = inr x
```

Отдельная возможность для optional-значений в Core не требуется.

## 21. Что намеренно отсутствует в Core v0.1

Следующее находится вне нормативной Core-спецификации:

```text
bytes
fixed-width machine integers
floating point
mutable memory
pointers
files
networking
Unicode
threads
atomics
exceptions
objects
modules
recursive algebraic data types
linear types
content-addressed references
DAG transport
compression dictionaries
debug symbols
```

Отсутствие этих возможностей не означает, что их нельзя реализовать или добавить профилями. Оно означает, что получателю не требуется понимать их для реализации NEX-1 Core.

## 22. Вычислительная полнота

Комбинация:

```text
lambda abstraction
application
natural numbers
zero test
successor/predecessor
typed fixed point
```

образует PCF-подобный язык с общей рекурсией. Поэтому NEX-1 намеренно допускает не завершение и подходит как основа универсальных вычислений.

Это отличается от simply typed lambda calculus без общей рекурсии, который strongly normalizing и поэтому недостаточен как единственная основа неограниченного языка общего назначения.

---

## 23. Bootstrap-модель

Минимальному получателю нужны четыре логических компонента:

```text
bit decoder
scope validator
type inference / unification
evaluator + primitive table
```

Bootstrap-процесс:

```text
bit stream
   -> decode Core term
   -> validate de Bruijn scope
   -> infer/check types
   -> evaluate
```

После появления первой реализации реализация NEX сама может быть выражена программой NEX. Self-hosting является целью проекта, но не требованием для совместимой реализации v0.1.

---

## 24. Внешние профили

NEX-1 Core не определяет машинный I/O.

Профиль MAY добавлять primitive ID `>= 32` и атомарные типы, необходимые конкретному окружению выполнения.

Профиль MUST NOT изменять смысл Core primitive ID `0..10` или кодировки Core-конструкторов.

Программа, требующая внешний профиль, корректна только если этот профиль явно выбран транспортным или execution environment.

Такое разделение позволяет одному Core-языку работать на несвязанных системах, не превращая указатели, файлы, сокеты, дисплеи или host ABI в часть универсальной спецификации.

---

## 25. Экспериментальное направление SYS0 (ненормативное)

Первый системный профиль предполагается использовать для исследования байт-адресуемой памяти с явными эффектами.

Кандидаты на профильные типы:

```text
Byte
Mem
```

Кандидаты на примитивы начиная с ID 32:

```text
byte      : N -> Byte
nat       : Byte -> N
and8      : Byte -> Byte -> Byte
or8       : Byte -> Byte -> Byte
xor8      : Byte -> Byte -> Byte
shl8      : Byte -> N -> Byte
shr8      : Byte -> N -> Byte
memNew    : N -> Mem
memSize   : Mem -> N
memLoad   : Mem -> N -> (1 + Byte)
memStore  : Mem -> N -> Byte -> (1 + Mem)
```

Этот раздел намеренно ненормативен в v0.1. SYS0 требует отдельного анализа семантики ресурсов, эффективности реализации и взаимодействия с полиморфизмом до превращения в спецификацию профиля.

## 26. Классы совместимости

### 26.1 Decoder

Совместимый **NEX-1 Decoder** MUST:

- декодировать каноническую грамматику термов;
- точно декодировать `U(n)`;
- обнаруживать неполные или структурно некорректные потоки;
- сообщать количество потреблённых битов.

### 26.2 Type checker

Совместимый **NEX-1 Type Checker** MUST:

- проверять область видимости de Bruijn;
- реализовывать rank-1 let-полиморфизм;
- выполнять унификацию с occurs check;
- корректно инстанцировать схемы примитивов;
- отвергать плохо типизированные термы.

### 26.3 Evaluator

Совместимый **NEX-1 Evaluator** MUST:

- принимать только валидные, хорошо типизированные замкнутые Core-термы;
- реализовывать семантику Core-примитивов;
- для завершающихся Core-программ выдавать результат, наблюдаемо эквивалентный эталонной weak call-by-name семантике.

## 27. Открытые вопросы для v0.2

Следующие вопросы намеренно оставлены нерешёнными:

1. Окупает ли `Let` стоимость в wire-представлении по сравнению с альтернативными способами кодирования полиморфизма?
2. Должен ли `Nat` оставаться arbitrary precision во всех реализациях или системный профиль должен добавить эффективные fixed-width words?
3. Является ли call-by-name лучшей эталонной семантикой или call-by-value настолько уменьшит сложность bootstrap, что изменение будет оправдано?
4. Следует ли добавить рекурсивные алгебраические типы в Core или оставить их кодированными/библиотечными структурами?
5. Должен ли будущий канонический transport использовать DAG sharing и content-addressed references?
6. Какова измеренная полная информационная стоимость относительно BLC, SKI/Jot, маленькой stack machine и WebAssembly?
7. Насколько маленьким может быть self-hosting decoder/type-checker/evaluator, написанный на самом NEX?

Ни один ответ на эти вопросы не является частью v0.1.

## 28. Обязательный экспериментальный корпус

До продвижения NEX-1 дальше v0.1 реализации SHOULD измерить как минимум:

```text
identity
constant function
function composition
addition
multiplication
factorial
Fibonacci
pair/sum processing
binary data traversal
parser or recognizer
a small interpreter
NEX decoder
NEX type checker
```

Для каждой программы необходимо фиксировать:

```text
wire bit length
AST node count
evaluation steps
peak runtime memory
implementation size
```

Эти измерения необходимы, чтобы определить, действительно ли NEX минимизирует целевую совокупную информационную стоимость, а не просто имеет привлекательное маленькое ядро.

## 29. Исследовательская база

NEX-1 является новым экспериментальным дизайном, но его отдельные основания являются установленными идеями:

- N. G. de Bruijn, *Lambda Calculus Notation with Nameless Dummies, a Tool for Automatic Formula Manipulation* (1972): безымянные связанные переменные / индексы de Bruijn.
- John Tromp, *Binary Lambda Calculus*: компактное prefix-free бинарное кодирование lambda-термов с de Bruijn-подобным представлением.
- Robin Milner, *A Theory of Type Polymorphism in Programming* (1978): полиморфный статический вывод типов.
- Luis Damas и Robin Milner, *Principal Type-Schemes for Functional Programs* (1982): principal type schemes для типизации в стиле Hindley-Milner.
- Gordon Plotkin, PCF и связанные работы о типизированных функциональных вычислениях с натуральными числами и фиксированными точками.
- WebAssembly Core Specification: современный пример разделения переносимого вычислительного ядра и взаимодействия с окружением.

Полезные первичные источники:

- https://doi.org/10.1016/1385-7258(72)90034-0
- https://tromp.github.io/cl/Binary_lambda_calculus.html
- https://doi.org/10.1016/0022-0000(78)90014-4
- https://doi.org/10.1145/582153.582176
- https://www.w3.org/TR/wasm-core/

## 30. Правило версионирования

Точные префиксные коды конструкторов и назначения примитивов в этом документе определяют **NEX-1 Core v0.1**.

Любое несовместимое изменение:

- кодирования конструкторов термов;
- целочисленного кодирования `U(n)`;
- соглашения о нумерации de Bruijn;
- правил вывода типов;
- primitive ID `0..10`;
- семантики примитивов;

требует новой версии Core.

Аддитивные внешние профили не изменяют версию Core.
